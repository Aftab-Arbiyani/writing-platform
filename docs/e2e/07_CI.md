# E2E 07 — Continuous Integration

> **Status:** Binding. Defines the `web-e2e.yml` GitHub Actions workflow that runs the browser suite in
> CI — mirroring the existing backend `e2e.yml` (same Postgres/Redis/MinIO wiring + migrations + seed),
> adding Playwright browser install, both built apps served, the three-engine matrix, sharding, and
> failure-diagnostic artifacts. Also sets the **gate policy** (when E2E becomes blocking).

---

## 1. What we reuse from the existing `e2e.yml`

The backend `e2e.yml` already establishes the real-infra pattern we copy verbatim:

- **Service containers:** `postgres:16-alpine`, `redis:7-alpine`, MinIO run as a background container
  with a created `qalam-media` bucket (GH service containers can't set MinIO's `server` command).
- **Env baseline:** `DATABASE_URL`, `REDIS_URL`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, the `S3_*`
  block, `SMTP_URL`, `SCHEDULER_ENABLED: 'false'` (cron must not fire mid-suite; workers stay on so
  queue-backed flows still process).
- **Toolchain:** `pnpm/action-setup@v4` (9.12.0), `actions/setup-node@v4` (node 24, pnpm cache),
  `pnpm install --frozen-lockfile`.

`web-e2e.yml` starts from that job and adds the browser + app layer. Where backend `e2e.yml` runs
`pnpm test:e2e` (supertest against the API), `web-e2e.yml` builds+serves both apps and runs Playwright.

**Additions over backend e2e:** **Mailpit** as a container (`axllent/mailpit`, SMTP `:1025` + API `:8025`)
so email flows are testable, pointing `SMTP_URL` at it.

## 2. Job shape (`.github/workflows/web-e2e.yml`)

```yaml
name: Web E2E

on:
  workflow_dispatch:
  push:
    branches: [main] # non-blocking on merge, matching current e2e.yml posture (until §6)
  # pull_request:              # ENABLED at Phase 2 exit — see §6 gate policy

concurrency:
  group: web-e2e-${{ github.ref }}
  cancel-in-progress: true

jobs:
  web-e2e:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        browser: [chromium, firefox, webkit] # all three, every run (docs/e2e/00 §5.2)
        shard: [1, 2] # split specs per browser for wall-clock (§4)
    services:
      postgres: { image: postgres:16-alpine, ... } # identical to e2e.yml
      redis: { image: redis:7-alpine, ... }
    env:
      NODE_ENV: test
      DATABASE_URL: postgresql://qalam:qalam@localhost:5432/qalam
      REDIS_URL: redis://localhost:6379
      JWT_ACCESS_SECRET: ci-access-secret-not-a-real-secret-000000
      JWT_REFRESH_SECRET: ci-refresh-secret-not-a-real-secret-00000
      S3_ENDPOINT: http://localhost:9000
      S3_REGION: us-east-1
      S3_BUCKET: qalam-media
      S3_ACCESS_KEY: minioadmin
      S3_SECRET_KEY: minioadmin
      SMTP_URL: smtp://localhost:1025 # → Mailpit
      SCHEDULER_ENABLED: 'false'
      CI: 'true'
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 9.12.0 }
      - uses: actions/setup-node@v4
        with: { node-version: 24, cache: pnpm }

      - name: Start MinIO + create bucket # copied from e2e.yml
        run: |
          docker run -d --name minio -p 9000:9000 \
            -e MINIO_ROOT_USER=minioadmin -e MINIO_ROOT_PASSWORD=minioadmin \
            minio/minio server /data
          for i in $(seq 1 30); do curl -sf http://localhost:9000/minio/health/ready && break || sleep 2; done
          aws --endpoint-url http://localhost:9000 s3 mb s3://qalam-media || true
        env:
          {
            AWS_ACCESS_KEY_ID: minioadmin,
            AWS_SECRET_ACCESS_KEY: minioadmin,
            AWS_DEFAULT_REGION: us-east-1,
          }

      - name: Start Mailpit
        run: docker run -d --name mailpit -p 1025:1025 -p 8025:8025 axllent/mailpit

      - run: pnpm install --frozen-lockfile

      - name: Build shared packages + both apps # CI serves BUILT output (docs/e2e/01 §4)
        run: pnpm --filter "@qalam/*" build && pnpm --filter frontend build && pnpm --filter admin build

      - name: Start backend, migrate, seed
        run: |
          pnpm --filter backend build
          node backend/dist/main.js &             # or `pnpm --filter backend start:prod`
          e2e/scripts/wait-health.sh http://localhost:4000/health
          pnpm --filter backend migration:run
          pnpm --filter backend seed
          pnpm --filter backend seed:e2e          # the e2e-fixtures seed (docs/e2e/04 §3)

      - name: Install Playwright browser
        run: pnpm --filter e2e exec playwright install --with-deps ${{ matrix.browser }}

      - name: Run E2E ( ${{ matrix.browser }} shard ${{ matrix.shard }} )
        run: >-
          pnpm --filter e2e exec playwright test
          --project=frontend-${{ matrix.browser }} --project=admin-${{ matrix.browser }}
          --shard=${{ matrix.shard }}/2
        env:
          E2E_API_URL: http://localhost:4000/api/v1

      - name: Upload report + traces
        if: ${{ !cancelled() }}
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report-${{ matrix.browser }}-shard${{ matrix.shard }}
          path: |
            e2e/playwright-report/
            e2e/test-results/
          retention-days: 14
```

> The `webServer` block in `playwright.config.ts` serves the two apps via `vite preview` on the built
> output (CI branch of the config, [01 §5](./01_Architecture.md)); the job above only needs the backend
>
> - infra up first. `--with-deps` installs the OS libraries WebKit/Firefox need on the runner.

## 3. The browser matrix — all three, managed for cost

The matrix runs **chromium × firefox × webkit**, and within each, both app projects. `fail-fast: false`
so a WebKit failure doesn't cancel the Chromium leg — we want the full cross-engine picture on every run.

**Cost trade-off (acknowledged):** three engines ≈ 3× the compute of a single-engine run. We accept it
per the explicit "in-depth, all three browsers every phase" decision ([00 §5.2](./00_Overview.md)), and
manage wall-clock with sharding (§4) rather than by dropping an engine.

---

## 4. Sharding

Each `(browser)` leg splits its specs into `--shard=N/2` across two matrix entries, so the six real
projects run as **6 legs × 2 shards = 12 parallel jobs**. As the suite grows past Phase 2, bump the
shard count (`shard: [1,2,3,4]` + `--shard=N/4`). **Why shard instead of more workers-per-job:** GH
runners are small (2 vCPU); three browser engines already saturate one runner's workers. Horizontal
shards give real parallelism across runners.

The HTML report is a **blob report** per shard; a final `merge-reports` step (optional, Phase 2+) merges
all shards/browsers into one combined HTML report artifact.

## 5. Failure diagnostics (the payoff)

Per [01 §5](./01_Architecture.md) config: `trace: 'on-first-retry'`, `screenshot: 'only-on-failure'`,
`video: 'retain-on-failure'`, HTML reporter + `github` reporter (annotates the PR/commit with failures).
On any failure the uploaded artifact contains:

- **Trace** (`.zip`) — open with `pnpm --filter e2e exec playwright show-trace <file>`: a clickable
  timeline with DOM snapshots, network, console, and the exact failing step.
- **Screenshot** at the point of failure.
- **Video** of the whole failing test.

Artifacts are named per browser+shard and retained 14 days. **Why on-first-retry, not always:** traces
are large; capturing them only when a test misbehaves keeps artifact storage sane while still catching
every real failure.

## 6. Gate policy — when E2E blocks a PR

Matching the current non-blocking posture of backend `e2e.yml` (docs 18: "e2e becomes a blocking gate
once infra is automated"):

| Stage            | Triggers                              | Blocking?          |
| ---------------- | ------------------------------------- | ------------------ |
| Phase 1          | `workflow_dispatch`, `push: main`     | **No** (advisory)  |
| **Phase 2 exit** | + `pull_request`                      | **Yes — required** |
| Phase 3–4        | `pull_request`, `push: main`, nightly | **Yes — required** |

The switch to blocking happens only after Phase 2 is green three consecutive runs with zero quarantine
([06 §4](./06_PhasePlan.md)). **Why gate at Phase 2, not Phase 1:** Phase 1 is the harness bring-up;
gating on a suite that's still stabilizing trains people to bypass it. Gate once it's trustworthy.

A **nightly** scheduled run (`schedule: cron`) runs the full suite (all phases, no shard filter) once
Phase 3 lands, catching flake and environment drift that a PR-scoped run might miss.

## 7. Relationship to the existing pipelines

- `ci.yml` (lint/typecheck/unit) stays the fast PR gate; `web-e2e.yml` is the slower integration gate.
- `web-e2e.yml` is a **sibling** of backend `e2e.yml`, not a replacement — they test different layers
  (API contract vs browser workflow) and can run in parallel.
- Deploy workflows (`deploy-staging.yml`, `deploy-production.yml`) may, post-Phase-4, run a **smoke
  subset** (`--grep @smoke`) against the deployed environment as a post-deploy health gate. Design that
  when Phase 4 is stable; out of scope until then.
